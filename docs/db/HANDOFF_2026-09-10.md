## RISKS

**R1 — #3 breaks the live heartbeat writer unless it is re-pointed first.**
The writer currently targets `public.agentic_heartbeats` (~every 2–3 h on
weekdays). After #3 the table is `equity.agentic_heartbeats`; `equity` is not
a PostgREST-exposed schema and there is deliberately no `public` synonym. If the
writer uses supabase-js/PostgREST it needs `.schema('equity')` **and** `equity`
added to *API → Exposed schemas*; if it uses a direct Postgres connection it
needs the schema-qualified name. It must use `service_role` (or `postgres`):
anon has no access at all in `equity`, authenticated is SELECT-only under RLS.
Today's RLS-with-no-policies already blocks anon/authenticated inserts, so the
writer is almost certainly service_role — confirm with the equity desk before
go. Sequence, `id` default and existing 43 rows move intact (rehearsed).

**R2 — 1b changes anon behaviour on `public.user_roles`.** Its four RLS
policies (`TO public`) call `has_role(...)`. Postgres checks EXECUTE at plan
init, so any anon statement touching `user_roles` now fails with
`permission denied for function has_role` instead of returning 0 rows.
The React app does not query `user_roles` or call `has_role` directly (grep of
`src/`, `supabase/functions/`, `atlas/apps/core-node/src/`), and the backend
RPC `upsert_account_metrics` runs with the service key, so no known caller
breaks. Authenticated keeps EXECUTE on `has_role` — admin policies keep working.

**R3 — 1b revokes EXECUTE on trigger functions from authenticated/anon and
(via `PUBLIC`) from `supabase_auth_admin`.** This is safe: Postgres checks
EXECUTE on a trigger function only at `CREATE TRIGGER` time, never when the
trigger fires. Rehearsed: an authenticated `UPDATE positions` still runs
`handle_updated_at`; a `supabase_auth_admin` `INSERT auth.users` still runs
`handle_new_user` (profile/role/metrics rows created). Direct calls
(`SELECT handle_updated_at()`) are denied, which is the intent. Do NOT
re-`CREATE TRIGGER` as anon/authenticated afterwards — that path *would* fail.

**R4 — repo lineage vs live function body.** `main` carries
`20260303183623_fix_upsert_account_metrics_equity_calculation.sql` (50k base
equity + all-time realized PnL, computed `daily_pnl_r`/`risk_heat`), but prod's
live body is the older `20251016000000` one. #2 keeps live prod semantics
(no behaviour change on prod) but on a Supabase Preview branch built from the
chain it *replaces* the `20260303183623` equity calc. If the desk wants the
50k-base calc back, that is a separate DBE decision; #2 lands as handed off.
Also note the LATERAL price lookup has no `o.user_id = p_user_id` filter (same
as live).

**R5 — #2 is a one-shot backfill; NULLs can reappear.** `handle_new_user()`
inserts `account_metrics (user_id)` with `execution_mode`/`session_id` NULL,
and neither column gets a DEFAULT or NOT NULL here. Verify "zero NULLs"
immediately after apply. Follow-up candidate (not in this PR):
`ALTER TABLE account_metrics ALTER COLUMN execution_mode SET DEFAULT 'paper'`.
`session_id` legitimately stays NULL for `account_metrics` days with no
session (`execution_mode` falls back to `'paper'`).

**R6 — attribution semantics in #2.** Backfill maps each `account_metrics`
row to the session started on the same UTC day, preferring the still-open
session, then the latest `started_at`; mixed-mode days take the latest
session's mode. `upsert_account_metrics` stamps today's row with the user's
*latest* session (open first), which may be a previous day's session if none
started today. `DATE()` uses the DB session time zone (UTC on Supabase).

**R7 — 1a widens nothing but can narrow reads.** With `security_invoker`,
queries on the three views run under the caller's privileges and the base
tables' RLS. Any consumer that relied on the views bypassing RLS (they were
executing as owner `postgres`) sees fewer rows. Intended.

**R8 — stub re-run caveat.** The stub is `IF NOT EXISTS` against `public`.
It must never be hand-run after #3: it would recreate an empty
`public.agentic_heartbeats`, and a re-run of #3 would then fail on
`SET SCHEMA` (relation already exists in `equity`). Supabase's runner never
re-applies a recorded version, so this only matters for manual SQL.
